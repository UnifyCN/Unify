## Vision

### 10x Check
Instead of just personalizing existing content — make Unify feel like it was built specifically for each user. Dynamic checklist generation by persona+location+time, AI Companion that opens with context-aware guidance, Learn pathway engine with progress tracking, smart community matching by topic overlap, and location-aware everything. A newcomer completes onboarding and immediately thinks: "This app was made for someone exactly like me."

### Platonic Ideal
A newcomer downloads Unify, completes a 2-minute onboarding, and the entire app reshapes itself around their situation. The checklist shows exactly what they need in their city. Learn content matches their interests and knowledge gaps. The Companion greets them by context. Groups feel hand-picked. And as their situation evolves (they get a job, pass a language test, get PR), the app evolves with them. Every surface reflects their journey — past, present, and future.

## Architecture Decision
**Approach B: Personalization Service** — A single Supabase edge function (`personalize`) that takes a user_id and returns ranked/filtered content for all surfaces (checklist, learn, groups, companion context). Server-side logic enables iteration without app updates.

**Sanity integration**: Learn module metadata (tags, persona relevance, interest categories) is synced to a `learn_modules` Supabase table via a Sanity webhook that fires on content publish. Fallback: manual sync CLI command (`sync-sanity-modules`). The edge function queries this table, NOT Sanity directly — avoids external API latency and cold-start issues.

**Caching strategy**: Client caches the personalize response for 15 minutes (React Query `staleTime`). Cache invalidated via `queryClient.invalidateQueries(['personalize'])` on these code paths: (1) onboarding quiz completion, (2) redo quiz from settings, (3) re-personalization prompt submission, (4) city/province update from migration prompt. Edge function uses Supabase's built-in response caching where possible. Social proof aggregate counts are materialized views refreshed hourly.

**Loading states**: Each surface shows its cached/stale data immediately while the personalize call is in-flight (React Query `keepPreviousData: true`). First-time users (no cache) see the current un-personalized default — content appears instantly, then re-ranks when personalization data arrives. No skeleton screens needed.

**Response time budget**: Edge function must respond in <500ms p95. Achieved by: (1) all reads from Supabase tables (no external APIs), (2) pre-computed aggregate counts, (3) simple scoring logic (weighted sum, not ML). The function accepts an optional `surfaces` query param (e.g., `?surfaces=checklist,companion`) so the client can request only what it needs for the current tab — reduces payload and compute for partial calls.

## Key Design Decisions
- **Location input**: Dropdown of major Canadian cities (top 20) + provinces + "Other (specify)"
- **Service shape**: Single edge function returning all personalized data in one call
- **Feature flags**: PostHog feature flag (`personalization_enabled`) — toggleable from dashboard without app deploy
- **Onboarding extension**: Add location step to existing 10-step quiz (becomes 11 steps)
- **Temporal rules**: Checklist items have `show_after_days` and `show_before_days` fields relative to `arrival_date`. Seasonal items have `month_start` and `month_end` fields. Rules stored in a `personalized_checklist_tasks` table. Note: `arrival_date` already exists in `onboarding_profiles` (collected in step 4 of the existing quiz as an ISO date string).
- **"Why this?" strings**: Template-based, returned by the personalize function alongside each item. Templates: "Recommended for {persona} in {city}", "Popular with newcomers who share your goals", "Relevant to your interest in {interest}".
- **Social proof cohort**: Same persona + same province. Minimum threshold of 5 users before showing count (privacy).
- **Recommendation event logging**: Log `(user_id, surface, item_id, rank, timestamp)` to a `recommendation_events` table for future analysis and ML training data.
- **Re-personalization trigger**: 3 months since last `updated_at` on `onboarding_profiles`. Shows a bottom-sheet: "Your situation may have changed — update your profile for better recommendations." If dismissed, snooze 30 days, then re-surface once more. If dismissed twice, stop asking.
- **Milestone thresholds**: Celebrations trigger at 25%, 50%, 75%, and 100% of personalized checklist completion. Treatment: brief confetti animation (Reanimated) + encouraging toast message. At 100%: modal with summary of accomplishments.

## Fallback Behavior
If the personalize edge function fails, times out, or returns an error:
- **Checklist**: Falls back to current behavior (persona + stage ordering only)
- **Learn**: Shows all modules in default Sanity order (no filtering)
- **Gather/Groups**: Shows all groups by creation date (current behavior)
- **Companion**: Sends messages without profile context (current behavior)
Each surface checks for the error independently — one surface failing doesn't affect others.

## Existing User Migration
Existing users who completed onboarding without city/province:
- On next app open, show a one-time inline prompt: "Add your city for personalized local resources"
- If dismissed, personalization service treats missing location as province-level or "Canada-wide" fallback
- Re-surfaces via the profile completeness nudge mechanism

## Privacy
- Location is user-provided (dropdown selection), not GPS-derived
- Stored in `onboarding_profiles` alongside existing data
- User can update/delete via settings (redo onboarding quiz)
- "People like you" counts require minimum 5 users in cohort to display (anti-deanonymization)
- Recommendation event logs retain for 90 days, then aggregated and purged

## Scoring Model
Each content item (checklist item, learn module, group) receives a relevance score:

```
score = (persona_match × 0.30) + (location_match × 0.25) + (interest_overlap × 0.20)
      + (goal_overlap × 0.15) + (temporal_relevance × 0.10)

Where:
  persona_match:      1.0 if item.persona = user.persona, 0.3 if item.persona = 'all', 0 otherwise
  location_match:     1.0 if item.province = user.province, 0.3 if item.province IS NULL (applies everywhere), 0 otherwise
  interest_overlap:   |item.interests ∩ user.learning_interests| / |item.interests| (0 if item has no interests)
  goal_overlap:       |item.goals ∩ user.goals| / |item.goals| (0 if item has no goals)
  temporal_relevance: 1.0 if within show_after/before window, 0.5 if within 7 days of window, 0 otherwise
  priority_boost:     item.priority / 10 (range 0.0 - 1.0, used as tiebreaker: added × 0.05)

Note: onboarding_profiles already has: persona, arrival_date, goals (text[]),
learning_interests (text[]), hobbies (text[]), outcomes_interested_in (text[]).
Only city and province are new columns (see ALTER TABLE below).
```

Items with score < 0.1 are filtered out. Remaining items sorted by score descending. Ties broken by creation date (newest first).

## New Table Schemas

```sql
-- Extend existing personalized_checklist_tasks table (NOT creating new table)
ALTER TABLE personalized_checklist_tasks ADD COLUMN province TEXT;
ALTER TABLE personalized_checklist_tasks ADD COLUMN goals TEXT[];
ALTER TABLE personalized_checklist_tasks ADD COLUMN show_after_days INT;
ALTER TABLE personalized_checklist_tasks ADD COLUMN show_before_days INT;
ALTER TABLE personalized_checklist_tasks ADD COLUMN month_start INT;
ALTER TABLE personalized_checklist_tasks ADD COLUMN month_end INT;
ALTER TABLE personalized_checklist_tasks ADD COLUMN priority INT DEFAULT 0;

-- Learn module metadata (synced from Sanity via webhook)
CREATE TABLE learn_modules (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  sanity_id TEXT UNIQUE NOT NULL,
  title TEXT NOT NULL,
  personas TEXT[],                 -- relevant personas
  interests TEXT[],                -- matching learning_interests
  goals TEXT[],                    -- matching goals
  province TEXT,                   -- NULL = all provinces
  difficulty TEXT,                 -- 'beginner' | 'intermediate' | 'advanced'
  synced_at TIMESTAMPTZ DEFAULT now()
);

-- Learn progress tracking
CREATE TABLE learn_progress (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id UUID REFERENCES auth.users NOT NULL,
  module_id TEXT NOT NULL,         -- sanity module ID
  status TEXT DEFAULT 'not_started', -- 'not_started' | 'in_progress' | 'completed'
  completed_at TIMESTAMPTZ,
  UNIQUE(user_id, module_id)
);

-- Checklist completion tracking
CREATE TABLE checklist_completions (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id UUID REFERENCES auth.users NOT NULL,
  checklist_item_id UUID NOT NULL,  -- references personalized_checklist_tasks
  completed_at TIMESTAMPTZ DEFAULT now(),
  UNIQUE(user_id, checklist_item_id)
);

-- Recommendation event log (for future ML)
CREATE TABLE recommendation_events (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id UUID REFERENCES auth.users NOT NULL,
  surface TEXT NOT NULL,            -- 'checklist' | 'learn' | 'groups' | 'companion'
  item_id TEXT NOT NULL,
  rank INT NOT NULL,
  created_at TIMESTAMPTZ DEFAULT now()
);

-- Social proof materialized view (refreshed hourly via pg_cron)
-- Phase 1: checklist only. Phase 2: extend to learn + groups.
CREATE MATERIALIZED VIEW social_proof_counts AS
SELECT
  p.persona,
  p.province,
  'checklist' AS surface,
  cc.checklist_item_id::text AS item_id,
  COUNT(DISTINCT cc.user_id) AS user_count
FROM checklist_completions cc
JOIN onboarding_profiles p ON p.user_id = cc.user_id
GROUP BY p.persona, p.province, cc.checklist_item_id
HAVING COUNT(DISTINCT cc.user_id) >= 5;

-- Add city/province to onboarding_profiles
ALTER TABLE onboarding_profiles ADD COLUMN city TEXT;
ALTER TABLE onboarding_profiles ADD COLUMN province TEXT;

-- Indexes
CREATE INDEX idx_learn_progress_user ON learn_progress(user_id);
CREATE INDEX idx_checklist_completions_user ON checklist_completions(user_id);
CREATE INDEX idx_recommendation_events_user_date ON recommendation_events(user_id, created_at);
CREATE UNIQUE INDEX idx_social_proof_unique ON social_proof_counts(persona, province, surface, item_id);

-- RLS Policies
ALTER TABLE personalized_checklist_tasks ENABLE ROW LEVEL SECURITY;
CREATE POLICY "Authenticated users can read checklist items"
  ON personalized_checklist_tasks FOR SELECT TO authenticated USING (true);

ALTER TABLE learn_modules ENABLE ROW LEVEL SECURITY;
CREATE POLICY "Authenticated users can read learn modules"
  ON learn_modules FOR SELECT TO authenticated USING (true);

ALTER TABLE learn_progress ENABLE ROW LEVEL SECURITY;
CREATE POLICY "Users can manage their own learn progress"
  ON learn_progress FOR ALL TO authenticated USING (auth.uid() = user_id);

ALTER TABLE checklist_completions ENABLE ROW LEVEL SECURITY;
CREATE POLICY "Users can manage their own completions"
  ON checklist_completions FOR ALL TO authenticated USING (auth.uid() = user_id);

ALTER TABLE recommendation_events ENABLE ROW LEVEL SECURITY;
CREATE POLICY "Users can insert their own events"
  ON recommendation_events FOR INSERT TO authenticated WITH CHECK (auth.uid() = user_id);

-- Scheduled jobs (pg_cron)
-- Refresh social proof materialized view hourly
SELECT cron.schedule('refresh-social-proof', '0 * * * *',
  'REFRESH MATERIALIZED VIEW CONCURRENTLY social_proof_counts');

-- Purge recommendation events older than 90 days (daily at 3 AM)
SELECT cron.schedule('purge-old-recommendations', '0 3 * * *',
  'DELETE FROM recommendation_events WHERE created_at < now() - interval ''90 days''');
```

### Sanity Sync Reconciliation
- **Primary**: Sanity webhook fires on content publish → upserts `learn_modules` rows
- **Safety net**: Weekly `sync-sanity-modules` CLI command does a full diff (upsert new + delete orphaned rows)
- **Failure handling**: If webhook fails, stale data persists until next weekly sync — acceptable since Sanity content changes infrequently

### Companion System Prompt Injection
Template injected into the Gemini API system prompt via `gemini-proxy` edge function (reads profile from DB using auth token):
```
You are speaking with a {persona} who arrived in {city}, {province} on {arrival_date}.
Their goals: {goals_joined}.
Their interests: {learning_interests_joined}.
Tailor your responses to their specific situation, location, and goals.
Refer to local resources in {city} when relevant.
```
